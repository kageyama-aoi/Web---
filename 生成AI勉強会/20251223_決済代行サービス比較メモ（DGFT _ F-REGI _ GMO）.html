決済代行サービス比較メモ（DGFT / F-REGI / GMO）

決済代行サービス比較メモ

DGFT（ベリトランス）、F-REGI（コンビニ払い）、GMO を対象に、実務運用寄りの視点で比較したメモです。
特に「ベリトランス＋コンビニ支払いを主に使い、GMOは技術的には軽めに扱う」前提で整理しています。

想定読者：決済連携の運用設計・ログ設計・入金消込・電子帳簿保存法対応などを担う実務担当者。

1. まず押さえるべき比較ポイント
Summary

この3サービスを運用目線で比較する際、特に差が出るのは次の4点です。

  • API・通知の仕組み（同期/非同期、Webhook、バッチ）
  • 入金消込のしやすさ（ID体系、CSV仕様、リアルタイム性）
  • 未入金・エラー・再発行の運用
  • ログ・証跡設計（監査・電子帳簿保存法対応を見据えた記録構造）
2. 3サービスの全体比較
Overview

2-1. 全体比較表（運用寄り）

項目 DGFT（ベリトランス） F-REGI（コンビニ） GMO（簡略）
主用途 クレジットカード＋総合決済（コンビニ・ID決済など） コンビニ払い特化の収納代行 コンビニ払い・Pay-easy・口座振替など幅広くカバー
API方式 RESTベース＋非同期通知（Webhook） REST/POST＋非同期通知（Webhook）＋日次CSV サービスによって SOAP/REST 混在、バッチ処理が多め
ID体系 orderId を軸に決済を一元管理 transactionId や支払票番号と紐付く構造 orderId と paymentId の2階層管理が必要なケースが多い
入金通知 Webhook による即時通知が基本 Webhook（即時）＋日次CSVによる補完 日次バッチ中心でリアルタイム性は相対的に弱い
CSV仕様 構造が比較的シンプルで扱いやすい 店舗コード・受付番号など項目が多く、やや複雑 項目が多く冗長になりがちで、前処理が前提
運用負荷（感覚値） 低〜中（統一思想で管理しやすい） 中（店舗別の例外処理が肝） 中〜高（バッチ＆多項目CSVの扱いで工夫が必要）
3. 技術的な仕組みの違い
Mechanism

3-1. DGFT（ベリトランス）

APIの特徴

  • RESTベースで実装されており、HTTP＋JSON の一般的なパターンで扱いやすい。
  • orderId をキーとして、同一注文に紐づく複数の決済イベント（成功／失敗／再決済など）を追跡しやすい。
  • 非同期通知（Webhook） が提供されており、決済完了やエラーがイベントドリブンに飛んでくる。
  • クレカ・コンビニ・ID決済など、決済手段が増えても基本思想は統一されていることが多い。

運用上のポイント

  • ログ設計がシンプルにできる：orderId を軸にしておけば、クレカの失敗→再決済→成功の履歴が1本の線で追える。
  • 電子帳簿保存法対応の証跡設計にも向きやすい：イベントログ構造が素直なため、監査用のトレースもしやすい。

3-2. F-REGI（コンビニ払い）

API・通知の特徴

  • コンビニ払いに特化し、支払票番号（バーコード番号等）を発行するフローが中心。
  • 支払い完了は 非同期のWebhook による通知が基本。
  • Webhookとは別に、日次の入金CSV で補完・照合を行う運用が前提となることが多い。
  • コンビニ店舗ごとに若干の仕様差（項目やタイミングの違い）が存在し、例外対応が必要になることがある。

運用上のポイント

  • 未入金の扱いが重要：
    • 支払期限切れの自動キャンセル・状態更新
    • ユーザーからの支払票再発行依頼への対応
    • 店舗ごとの通知タイミングの差による一時的な不一致
  • CSV項目が多く複雑：
    • 店舗コード・受付番号・加盟店IDなど、キー候補が複数存在。
    • EmEditor や SQL での抽出・正規化テンプレートを用意しておくと運用が安定しやすい。

3-3. GMO（簡略）

特徴

  • コンビニ払い・Pay-easy・口座振替など、多数の決済手段をカバーする総合型。
  • バッチ処理が多い構成 があり、リアルタイム性より一括処理寄りの設計になっていることがある。
  • サービスによって API 仕様が揃っていない（SOAP/REST が混在する場合がある）。

運用上の注意点

  • 入金通知が日次バッチ中心になりがちで、リアルタイム反映が必要な業務とは相性を考える必要がある。
  • orderId と paymentId のように、2階層のID管理 を行うパターンがあり、設計時にキー設計を整理する必要がある。
  • CSVの項目数が多く冗長 なため、前処理・抽出ビュー・正規化テーブルの設計がほぼ必須。
4. 入金消込のしやすさ
Reconciliation

4-1. 比較表（入金消込観点）

項目 DGFT F-REGI GMO
キーの一意性 orderId 中心で高い一意性 支払票番号＋transactionId などの組み合わせ orderId＋paymentId の組み合わせ
CSVの扱いやすさ ◎：比較的シンプルでそのままSQL化しやすい △：項目が多く、前処理テンプレートが欲しい △：冗長なため、抽出ビュー設計が前提
SQL化のしやすさ ◎：正規化や集計ビューを作りやすい ○：正規化すれば扱いやすいが初期設計はやや重め △：設計しないと「とりあえずCSV結合」になりやすい
ログ設計のシンプルさ シンプル：orderId 軸で統一しやすい 店舗別の例外考慮が必要 イベント種別・サービス種別の分解設計が必要
5. 入金消込・運用フロー
Flow

5-1. コンビニ払いの基本フロー（F-REGI想定）

① 支払票発行
   - F-REGI に決済情報を送信
   - 支払票番号・バーコード番号が発行される
   - 自社DBに「未入金」として登録

② Webhook 受信
   - ユーザーがコンビニで支払い
   - F-REGI から Webhook 通知（支払い完了）
   - 対応する注文を「入金済」に更新

③ 日次CSVで差分チェック
   - F-REGI から日次の入金CSVを取得
   - Webhookで取りこぼしたレコードがないか照合
   - 不整合があればログ出力・手動確認フローへ

④ 期限切れ処理
   - 支払期限を過ぎた未入金データをバッチで抽出
   - ステータスを「期限切れ」に更新
   - 必要に応じてユーザーへの通知や注文取消

⑤ 再発行対応
   - ユーザーからの問い合わせで支払票再発行が必要な場合
   - APIで再発行／新規支払票発行
   - 旧支払票の扱い（無効化か、並行有効か）を運用ルールで明確にしておく
6. 推奨ログ構造（イベント駆動＋監査向け）
Logging

6-1. 決済イベントログの例

どのサービスでも共通で扱えるよう、決済イベントを抽象化したテーブルを1つ用意しておくと便利です。

event_id              : イベントを一意に識別するID
order_id              : 自社側の注文ID（DGFTの orderId と対応）
payment_method        : 'credit', 'convenience', 'id_payment', など
provider              : 'DGFT', 'F-REGI', 'GMO' など
event_type            : 'created' / 'paid' / 'expired' / 'failed' / 'refunded' など
event_datetime        : プロバイダ基準 or 自社受信日時（両方あってもよい）
raw_payload           : 受信したJSONやCSV行をそのまま保持（JSON文字列等）
processed_flag        : 自社システム側で処理済かどうか（0/1）
created_at            : ログ登録日時
updated_at            : 最終更新日時

ポイント：

  • raw_payload をそのまま保存しておくことで、「過去に何が来たか」を正確に再現できる。
  • event_type を共通化しておくと、サービスをまたいだ横断集計がしやすい。
  • provider・payment_methodを分けておくことで、「F-REGI経由のコンビニ払い」などの切り出しが簡単になる。
